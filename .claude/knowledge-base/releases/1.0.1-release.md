## Why the cycle stops here and not further

`cycle-release § Hard gates` marks the PR-approval gate **LOCKED**: the merge always waits for a
human-approved PR, and auto-merging violates Unbreakable Rule 4. The previous release recorded
that the assistant merging the promotion PR was an override of exactly this gate — *"one merge,
authorized once, for this release; the gate is unchanged"* (B-229). Repeating it without a fresh
authorization would turn a recorded exception into a precedent, which is what the record exists to
prevent.

`PR_OPEN_AWAITING_APPROVAL` is a declared terminal verdict of this cycle, not a failure to run it.
The chain resumes automatically once #476 merges: tag `v1.0.1` on the merge commit, push it,
`gh release create`.

## Version derivation — chosen, not inferred

The bump was passed **explicitly as `patch`** rather than auto-derived, and the reason is recorded
because auto-derivation would have been wrong.

`[Unreleased]` carried a `### Removed` section, which `cycle-release § Bump-level derivation` reads
as **major**. Its only entry was the removal of a test-mock helper (`installSSEMocks`) with no
consumer surface. A 2.0.0 would have announced a breaking change to every consumer where none
exists. The entry moved to `### Changed`, labelled internal, so the rule stops misfiring on it in
future cycles.

Everything shipped here is a defect fix or a correction of wrong behaviour: no new feature, no API
change, nothing removed that a consumer can call. That is a patch, regardless of the 46-item
volume.

# Resumed and completed — 2026-08-12  ·  verdict: RELEASED

The run above halted at `PR_OPEN_AWAITING_APPROVAL` on 2026-08-11 and was never resumed. It left a
`## [1.0.1] - 2026-08-11` section in `CHANGELOG.md` announcing a release that did not exist: the
`develop → main` PR never merged and no `v1.0.1` tag was ever created, in this repository or on the
remote. Five days later the record still claimed it, and the work it described was still unreleased
(B-268).

That was found by *running* the release phase, not by reading — the bump level is derived from
`[Unreleased]`, and deriving it meant reading the sections above it.

## What was decided, and by whom

The owner chose to **ship the number for real** rather than let it vanish. `[1.0.1]` now carries
what it always claimed plus everything measured since, and its date moves from 2026-08-11 to
2026-08-12 — the first was the claim, the second is the fact.

**This diverges from the project's own bump rule, deliberately and on the record.**
`cycle-release.md § Bump-level derivation` maps a non-empty `[Unreleased] § Removed` to `major`,
which would have made this v2.0.0. The single `Removed` entry is the `ENGINE_URL` config value that
was validated at container start and read by no code — removing it breaks no consumer. The rule is
conservative by design and the derivation was followed mechanically first; the override is the
owner's, made at the human-approval gate that exists for exactly this, and recorded here rather
than applied quietly.

triggered by the `v1.0.0` tag. The `images` job — build, trivy, cosign, GHCR push — has never
