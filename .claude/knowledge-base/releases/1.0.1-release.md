## Why the cycle stops here and not further

`cycle-release § Hard gates` marks the PR-approval gate **LOCKED**: the merge always waits for a
human-approved PR, and auto-merging violates Unbreakable Rule 4. The previous release recorded
that the assistant merging the promotion PR was an override of exactly this gate — *"one merge,
authorized once, for this release; the gate is unchanged"* (B-229). Repeating it without a fresh
authorization would turn a recorded exception into a precedent, which is what the record exists to
prevent.

`PR_OPEN_AWAITING_APPROVAL` is a declared terminal verdict of this cycle, not a failure to run it.
The chain resumes automatically once #476 merges: tag `v1.0.1` on the merge commit, push it,
`gh release create`.

## Version derivation — chosen, not inferred

The bump was passed **explicitly as `patch`** rather than auto-derived, and the reason is recorded
because auto-derivation would have been wrong.

`[Unreleased]` carried a `### Removed` section, which `cycle-release § Bump-level derivation` reads
as **major**. Its only entry was the removal of a test-mock helper (`installSSEMocks`) with no
consumer surface. A 2.0.0 would have announced a breaking change to every consumer where none
exists. The entry moved to `### Changed`, labelled internal, so the rule stops misfiring on it in
future cycles.

Everything shipped here is a defect fix or a correction of wrong behaviour: no new feature, no API
change, nothing removed that a consumer can call. That is a patch, regardless of the 46-item
volume.
