## [0.11.0] - 2026-06-27

### Added
- **Account-level tenancy (M1): per-Account broker mint + ForwardAuth cross-account guard (lazy validation).** The per-tenant credential broker is now Account-aware — `KeyForTenantScoped(ctx, accountID, tenantID, scopes)` keys its cache by `account ∥ tenant ∥ scopes` (no cross-account cache sharing) but **never sends the account to the data-plane**: the minted key's `workspace_id` stays `== tenantID`, so theo-memory's isolation unit remains the tenant (unchanged seam). ForwardAuth gains an injected ownership authorizer (`auth.AccountOwnsTenant`): an Account-aware credential whose `account_id` does **not** own the targeted `tenant_id` is rejected with **403** (no Authorization header, no mint); a legacy NULL-account key (pre-M0) **skips** the check and still mints (200, backward-compat); a DB error in the check **fails closed** (503). The broker lazily trusts the ForwardAuth-validated relationship (it does not re-validate). Both the memory and theo-promptly brokers + their `Evict(tenantID)` (now matching the tenant as the middle cache-key segment) are updated. Proven under `go test -race` + an integration suite against pg-cloud (account-owns→200 with workspace==tenant, cross-account→403 no-mint, legacy→200, concurrent). (plan `account-broker-m1`, ROADMAP M1, ADR `account-level-tenancy`)

## [0.10.0] - 2026-06-27

### Added
- **Account-level tenancy (M0): the Account ("Cliente Theo") entity above the tenant.** A new `internal/account` package (`EnsureAccount`, idempotent + race-safe find-or-create, 1:1 owner↔account via `accounts.UNIQUE(owner_id)` + `ON CONFLICT`) is wired into `auth.EnsureTenant` so every new signup provisions an Account, then its default tenant, atomically in one transaction. `UserContext` gains `AccountID`; `auth.ResolveAPIKey` now SELECTs and surfaces `account_id` **NULL-tolerant** (a legacy `theo_live_*` minted before the migration resolves with `AccountID == ""`, never an error); `CreateKey` persists the caller's `account_id` (NULL when absent). The Account lives only in the control-plane — theo-memory and the `workspace_id == tenant_id` data-plane invariant are unchanged. Proven against real pg-cloud (`tests/e2e/account_m0_e2e_test.go`, build-tag `e2e`, run under `-race`): legacy key still resolves (200, empty Account), a new signup yields exactly one Account owning its tenant, and concurrent same-subject logins converge on a single account+tenant (no data race). Billing-per-account and `NOT NULL` enforcement are deferred to M2/M3. **Deploy ordering:** the `theo` migrations `000034`–`000039` (which add `account_id`) MUST be applied **before** this theo-cloud binary is rolled out — the binary's key lookup SELECTs `account_id`. If the column is absent (wrong order), auth fails **closed** (`ErrBackendUnavailable` → 503), never a silent breach; the standard Phase-1-migrations-first sequence avoids it. (plan `account-foundation-m0`, ADR `account-level-tenancy`)
- **Platform API Gateway M8 (slice 3a): Traefik unified as the single dev edge.** One `dev/traefik/dynamic.yml` now routes the whole dev surface on `:8090` — `kratos` (auth flows → kratos:4433), `bff` (`/v1`,`/engine`,`/health` → theo-cloud:13002), the M6 `memory-edge` capability (`/v1/memory` → ForwardAuth → themory:8080), and a `dashboard-spa` catch-all → a new `nginx:alpine` `dashboard` service serving the SPA with a history-API fallback (`try_files`, ADR D2). Capability routes are pinned above the BFF by explicit `priority` (memory 100 > bff 10 > spa 1) so a capability never falls into the BFF or SPA catch-all (ADR D3; rule-length already wins, the explicit priority is defense-in-depth). A `serversTransport: internal-tls` scaffold (serverName + rootCAs) is defined for the prod authz hop but left **unreferenced in dev** so `up` stays one command (ADR D4); the prod overlay flips the hop to https (`dev/traefik/README.md`). Config drift-guards (`tests/config`) pin every new router + precedence + the unreferenced-TLS invariant; per-route-class e2e (`tests/e2e/edge_unify_e2e_test.go`, build-tag `e2e`) assert SPA fallback, kratos single-origin (R2), and BFF reachability through the single edge. A prod-ingress ADR (`decisions/2026-06-25-prod-ingress-traefik-vs-gateway-api.md`) records Traefik-direct over Kubernetes Gateway API (ForwardAuth is not standardized in the Gateway API stable spec). (platform-edge-unify-slice3a, ADR D1–D4)

- **Platform API Gateway M6 (slice 1): ForwardAuth authz-brain endpoint (`/internal/authz/forward`).** A new `routes.ForwardAuthHandler` is the endpoint the Traefik edge delegates to per request: it validates the inbound `theo_live_*` (via `auth.ResolveAPIKey`), checks the required scope, mints the per-tenant downstream credential (via the Model B broker), and returns it as the `Authorization` response header on ALLOW (200) for the edge to inject upstream. Every DENY path (401 invalid key, 403 missing scope, **503 fail-closed** on a backend/mint error or empty mint — EC-1/EC-2) NEVER carries an `Authorization` header, so the edge copies nothing and makes no upstream call without an explicit ALLOW. Typed errors `ErrInvalidCredential` / `ErrBackendUnavailable` make an infra outage fail-closed (never reported as a bad key — EC-1); an empty-tenant row is rejected at the boundary (EC-3); a non-Bearer scheme is rejected without a DB hit (EC-6). `RequireScope` behavior is unchanged. (platform-api-gateway-edge-slice1 T0.1, ADR D1)

### Changed
